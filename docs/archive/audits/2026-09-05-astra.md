# Auditoria Astra de SolaraCommerce hacia 1.0

Fecha de inicio: 2026-09-05. Informe incremental solicitado por el usuario.

> **CONTEXTO HISTÓRICO DE PERSISTENCIA:** esta auditoría comenzó antes de la
> migración definitiva del 06/09/2026. Las menciones a la portable como ubicación
> de datos describen el estado observado en ese momento. La operación vigente usa
> `Abrir SolaraCommerce.cmd` y `proyectos/` del checkout como fuente comercial.

## Alcance y honestidad de la evidencia

- Se audita el working tree actual, incluidos cambios locales preexistentes. No se corrige codigo ni se modifica la data real de la portable.
- Objetivo: inventariar todas las familias funcionales y evaluar su estado, riesgos y requisitos para una excelente 1.0. Inventario completo no equivale a ejecutar el 100% de combinaciones de uso.
- Etiquetas: CONFIRMADO (evidencia directa), RIESGO (requiere reproduccion), RECOMENDACION (opinion de producto/ingenieria), PENDIENTE (sin validar).
- Severidades: P0 perdida de datos/seguridad critica; P1 bloqueante de flujo esencial; P2 defecto relevante o gap de calidad; P3 mejora/documentacion.
- Este archivo se actualiza durante la investigacion. Una seccion pendiente no representa aprobacion.

## Registro inicial

### A-001 | P2 | CONFIRMADO | El gate documentado de cierre no coincide con el ejecutable

Evidencia: `AGENTS.md:186-187` presenta `check` como alias de `check:full`; `package.json:23-24` define `check` como `check:fast`, mientras `check:full` agrega `check:slow` y build.

Impacto: alguien que siga la guia puede creer que completo el cierre sin budgets, benchmark, checks lentos ni build. Para 1.0 debe existir un contrato unico entre documentacion, scripts y CI. No implica que los tests fallen.

### A-002 | Contexto | CONFIRMADO | Auditoria sobre una revision no congelada

`git status --short` inicial muestra modificaciones previas en Studio, desktop, persistencia, exporter, tests y documentacion, ademas de archivos nuevos. No se revierten ni se atribuyen a esta auditoria. La aprobacion final de una release debe repetirse sobre un commit congelado y su artefacto portable correspondiente.

### A-003 | Alcance de producto | CONFIRMADO

Segun `AGENTS.md:9-22`, es un estudio local-first multitienda que exporta sitios estaticos con checkout por WhatsApp. No tiene backend remoto ni pagos online. Esto es una decision de alcance, no un bug. Una 1.0 excelente debe prometer exactamente este producto, no la operacion transaccional de una plataforma SaaS.

## Auditoria Studio

Auditoria estatica incremental de `apps/studio`, sin ejecutar la app sobre data ni modificar codigo. Documentos leidos: AGENTS, PROJECT_MAP, ARCHITECTURE y TESTING. CONFIRMADO significa traza determinista de codigo, no reproduccion de navegador, salvo indicacion expresa. Suites grandes delegadas al auditor principal.

### ST-001 | P1 | CONFIRMADO | Escape o X elimina el recovery draft

Traza: `apps/studio/src/App.tsx:798-811` espera una respuesta booleana y llama `clearRecoveryDraft` si es falsa. El dialogo conecta `onCancel` con `false` (`App.tsx:933-948`). `components/ConfirmDialog.tsx:50-57,91-97` llama ese mismo callback tanto con Escape como con X rotulada "Cerrar dialogo". Por tanto cerrar para decidir mas tarde equivale a "Descartar borrador" y elimina la unica copia de cambios no confirmados en disco. Criterio 1.0: cierre neutral conserva borrador; descarte debe ser accion destructiva explicita y separada. Prueba necesaria: abrir recovery, Escape/X, volver a abrir y verificar que el draft sigue disponible.

### ST-002 | P1 | CONFIRMADO | Importar respaldo deja obsoleta la version esperada de disco

Traza: `App.tsx:574-586` persiste el importado pero ignora el recibo y no llama `setActiveDiskVersion`, a diferencia de la importacion de recovery (`App.tsx:424-440`) y duplicacion (`609-630`). Studio recibe la version anterior (`563-566`); `features/ManagedPersistenceControls.tsx:80-94,125` la envia al siguiente guardado. Importar sobre la misma tienda incrementa disco de N a N+1 pero el siguiente Guardar usa N; importar otra tienda conserva la version de la tienda anterior. Impacto: conflicto de version espurio tras importacion exitosa. Criterio 1.0: propagar recibo y probar importar -> editar -> guardar sin conflicto, tanto mismo ID como ID distinto.

## Auditoria Persistencia y Desktop

Auditoria incremental por lectura estatica; no se accede a data real, no se empaqueta ni se ejecutan suites grandes. Documentos leidos: AGENTS.md, docs/INTEGRATIONS.md, docs/backup-and-recovery.md y docs/PORTABILITY.md. Los tests citados son evidencia de cobertura declarada, no ejecuciones aprobadas en esta auditoria.

### PD-001 | P0 | BUG CONFIRMADO | portable:clean elimina tambien las tiendas

`scripts/portable-clean.mjs:5-7` ejecuta rm recursivo de `.release/portable` sin backup, confirmacion ni preservacion. Esa ruta contiene la unica copia de tiendas reales segun `AGENTS.md:47-50`; `docs/PORTABILITY.md:73-74` la presenta como salida generada limpiable. El efecto destructivo se confirma por codigo, NO se ejecuto el comando. Criterio 1.0: limpieza que preserve proyectos/perfil o rechace presencia de datos y prueba aislada de preservacion.

### PD-002 | P1 | BUG CONFIRMADO | Sentinel ausente o distinto elimina IndexedDB completo

`apps/studio/src/lib/repository.ts:405-418` elimina `solara-commerce-studio` si localStorage no contiene la version esperada, antes de leer proyectos o recovery. No requiere consentimiento ni exportacion y elimina tambien recoveryDrafts (tabla en :133-142). La condicion incluye sentinel ausente con DB existente; no se afirma que haya sucedido en el perfil real. Criterio 1.0: migracion no destructiva y prueba con DB existente + sentinel ausente/antiguo; conservar borradores aun en modo gestionado.

## Auditoria Storefront y Modulos

Alcance exclusivo: `packages/storefront-runtime`, `packages/modules`, `packages/module-sdk`. Lectura de AGENTS.md, docs/PROJECT_MAP.md, docs/STOREFRONT_V2.md y docs/TESTING.md. Auditoria estatica incremental; sin cambios de codigo/data ni certificacion de navegador. Las pruebas citadas son cobertura existente, no ejecuciones nuevas salvo indicacion explicita.

### SM-001 | P2 | CONFIRMADO | El multipart limita partes omitiendo el detalle comercial restante

Traza: `packages/storefront-runtime/src/index.ts:504-605`: `splitOrderParts` limita a 12 partes (516), conserva 11 y agrega el resto en una parte resumida (600-604). `renderPart(..., true)` solo emite "...y N productos mas (incluidos en el total)" (551-558), sin identidades, variantes ni cantidades del resto. El total incluye esos productos. No es perdida de la data guardada, pero el mensaje no permite al vendedor reconstruir el pedido completo. Pendiente contrastar el tratamiento UI y tests antes de cerrar severidad. Criterio 1.0: nunca presentar como pedido completo un resumen sin detalle; bloquear con explicacion o proveer entrega completa verificable.

### Fortalezas Verificadas (Incremental)

- Carrito: cantidades enteras 1..99, validacion de precios enteros, strings y URLs; reconciliacion con catalogo y marcado de variantes retiradas, deduplicacion y limpieza de imagen obsoleta (`storefront-runtime/src/index.ts:140-291`). Persistencia primaria/respaldo y tolerancia a storage denegado (682-700, 837-856); datos personales no forman parte de `StoredCartLine`.
- SDK: escape de texto/atributos, protocolos permitidos y rich text con lista cerrada de tags/atributos (`module-sdk/src/index.ts:275-307,397-458`); SafeHtml es una marca TypeScript, no un sanitizador automatico (265-273). Imagenes con dimensiones, alt, lazy/eager, picture y MIME (533-625).

## Auditoria QA y Release

### QA-001 | P2 | CONFIRMADO | Un gate local verde admite errores

`scripts/check-quick.mjs:32-39,104-143` usa modo advisory por defecto fuera de CI, tolera errores de formato y ciertos timeouts del harness sin aserciones detectadas. `docs/TESTING.md:175-179` lo documenta. No es equivalente a validacion estricta. Para aprobar 1.0: ejecutar con `SOLARA_VALIDATION_MODE=strict` y conservar salida/commit/entorno, sin confundir "completado con advertencias" con "todo probado".

### QA-002 | P3 | CONFIRMADO | Documentacion historica mezcla estados y metricas

`docs/TESTING.md:266-267` dice full E2E pendiente; `docs/TECHNICAL_DEBT.md:21-23,40` registra un full Chromium posterior aprobado. AGENTS habla de 8 workers y TESTING de 3. Los datos historicos sirven como antecedentes, no como evidencia del working tree actual. Recomendacion: una ficha de release generada por maquina con revision, artifact hash, resultados, skips y fecha, manteniendo el historial aparte.
